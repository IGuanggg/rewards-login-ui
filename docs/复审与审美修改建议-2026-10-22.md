# 第二次验收与审美修改建议

检查日期：2026-10-22。对象：当前 `rewards-login-ui` v2 源码及本机服务。

## 明确结论

**整体仍不通过最终验收。基础 UI 已合格，视觉精致度和操作体验尚未达到成品标准。**

我的主观审美评分是 **6.5/10**。入口比第一版简洁，组件、圆角与深浅主题有统一性，基本信息也能读懂；但工作台仍然依靠渐变、光晕、标签和嵌套卡片营造完成感，真正需要用户注意的账号状态、下一步操作和授权结果反而没有足够清楚。这个评分只评价设计，不是功能测试通过率。

**与 CDK 的相似度，我主观给 4/10。** 两个分数评价的是不同事情。新版入口的居中单列结构较像，但参考项目使用中性色、较小的圆角和克制的按钮；其 `LiquidButton` 是悬停时的填充效果，并非持续流动的紫青渐变。本版仍保留极光、彩色流线和循环按钮动效，整体设计语言差别明显。此判断已核对参考项目的登录页、全局布局、主题与按钮源码；本次参考站实时截图读取超时，没有把它当成成功的页面实测。

本次确实有实质进步：我重新执行了现有的 23 项隔离回归检查，**23 项全部通过**。上次的接口完全无鉴权、无效目录写入、换行注入、自定义会话目录、指纹设置覆盖、401 状态误判等问题都已得到相应修复。

不过独立补测又确认了密码持久化、退出后凭证撤销、自检误报和无效会话成功判定的问题。并且本机正式 `config.json` 的 `botDir` 仍为空；当前目录中没有上游签到仓库。真实微软登录、服务重启后复用真实会话、真实签到均未验收。

## 必须先修的功能问题

### A. P1：8～15 字符的访问密码保存后，重启会失效

证据：`server.js:118` 加载配置时要求密码长度至少 16；`server.js:1303` 修改接口却允许至少 8。页面也明确提示“至少 8 位”。

独立复测：将测试密码改为 8 字符，接口返回 200；重启测试服务后，同一密码登录返回 401，配置中的密码已被随机新值覆盖。

修改：前端提示、服务端修改校验、配置加载校验使用同一个规则。不要把不满足新规则的已有密码静默替换；应给出迁移或设置提示。补充 8、15、16 字符的保存→重启→登录测试，且不要使用 `PANEL_TOKEN` 覆盖掉被测试的配置值。

### B. P1：退出后，旧 Cookie 在服务重启后重新有效

证据：`server.js:157` 的 `sessionEpoch` 只存在内存中，重启归零；Cookie 签名密钥又来自持久化密码。

独立复测：登录取得 Cookie → 退出 → 旧 Cookie 访问返回 401 → 重启 → 同一旧 Cookie 访问返回 200。

修改：如果需要服务重启后保留登录，就持久化会话和撤销信息；否则采用每次启动随机的会话签名材料，使重启前的 Cookie 一律失效。还应避免把 `/api/auth/logout` 设为无需认证的全局撤销入口：本次不带 Cookie 请求退出，就能使另一个有效会话失效。已有 SSE 连接也应考虑在退出时关闭。

### C. P2：环境自检会报告“就绪”，但缺少真正可运行的条件

证据：`server.js:681`、`server.js:704`。

已复现：

1. 仓库缺少 `config.json`，仍返回 `ready: true`，提示“首次运行会自动生成”。但上游手动登录工具会直接读取所需配置，缺失配置或缺少 `sessionPath` 会退出。
2. `config.json` 仅为 `{}` 时，自检仍认为配置正常。
3. 缓存里只有一个空的 `chromium_headless_shell-*` 目录，没有任何浏览器可执行文件，自检仍把 Chromium 标为已安装。
4. 已连接 A 实例后，传入 `?botDir=B` 检查新路径，`/api/preflight` 实际优先检查 A，可能为 B 显示 A 的结果。位置：`server.js:1262`。

修改：

- 将“浏览器授权需要的配置”和“签到运行需要的构建产物”分开自检，不要用一套模糊的“就绪”概括全部能力。
- 校验手动登录所需配置字段；缺失时明确提示初始化方法，不能承诺当前流程不会执行的自动生成。
- 从目标仓库解析实际安装的 Patchright，取得其对应的 Chromium 可执行文件路径，确认文件存在；需要更可靠时做有超时的启动并关闭探测。空缓存目录、不同版本的 Chromium、仅 headless shell 均不能作为可见浏览器授权可用的证据。
- 自检优先使用本次明确请求检查的路径；未提供时再使用当前已连接实例。

### D. P2：空 Cookie 或损坏会话仍被判成功

证据：`server.js:902`。现在核对了时间戳，确实比上一版可靠，但没有把会话内容能否解析、Cookie 是否非空纳入成功条件。

独立复测：模拟脚本分别写入 `cookies: []` 和无法解析的 `storage_state`，更新时间戳并正常退出，任务两次都变为 `done`。

修改：成功需要正常退出、对应账号和平台的会话确实更新、存储结构可解析、所需 Cookie 非空。读取异常要保留为明确错误。对合法状态只能表述“已保存会话”，不能据此保证未来一直有效。上游正常手动登录通常会拒绝保存空 Cookie，因此这是面板自身的健壮性缺口，不代表真实上游每次都会触发。

### E. 交付缺口：最初的“登录省事”仍然只完成了一半

证据：`server.js:920` 启动的仍是 `scripts/main/manualLogin.js`，参数只有邮箱、平台与 fresh；没有新增将页面保存的密码自动填入微软页面的实现。

当前功能减少了手改 `.env` 和输入命令的次数，但不能宣称已经减少了微软页面上的重复填表。单独增加一个需从终端查密码的面板入口，也会增加首次使用步骤。

修改方向：

- 明确区分“本机面板访问密码”和“微软账号登录”，避免让用户误会入口作用。
- 正常使用优先复用已保存会话；只有会话失效或用户主动重登时进入授权流程。
- 如果这次只做浏览器手动授权，默认只让用户填邮箱，密码和 TOTP 放入明确命名的自动登录配置中，并说明它们的实际用途。
- 如果要实现“账号密码填一次后自动登录”，必须另行接入、测试对应流程，并在需要验证码、通行密钥或二次验证时明确交给用户完成。不能把当前的手动授权入口改个名字就当成自动登录完成。
- 补齐本地上游仓库、依赖、浏览器和启动入口，再用真实账号验证首次授权→会话保存→重启→复用。已有模拟测试不能代替此项。

## 审美上具体哪里不够好

### 1. 装饰强于产品内容

紫青极光、持续游动的线条、流动渐变按钮、渐变头像、多个彩色状态标签同时出现。它们各自不难看，但叠加以后，页面缺少安静的视觉基础，也不太像参考项目的克制风格。

建议：

- 工作台移除流线和大面积极光；入口若保留光晕，降低到不影响文字的程度。
- 中性色背景配一个主要强调色。渐变只留在品牌标记，或只在主按钮悬停时轻微变化。
- 主按钮使用稳定背景，停止永久循环动画。绿、黄、红仅表达成功、待处理和失败。
- 不要继续加玻璃、立体阴影或新色彩，这一版更需要减法。

### 2. 账号信息被切成过多小标签

同一账号同时显示 `ACCOUNT_N`、两端 Cookie 数量、时间、密码、TOTP、地区、语言，几乎每项都有圆角边框。用户第一眼要判断的是“这个账号能否使用、下一步要做什么”，不是查看内部配置清单。

建议每行固定为：

```text
头像  demo.user@outlook.com                         [连接 / 重新授权] [更多]
      手机会话已保存 · 电脑会话已保存 · 5 分钟前
```

状态改为点状图标＋一行文字。Cookie 数、代理、TOTP、账号槽位、地区语言放入详情或编辑面板。删除放进“更多”，避免和常用操作同级。右上角全局显示总体环境；不要给每项配置都做高亮徽章。

### 3. 工作台的主要操作不够集中

右侧新增表单长期占据约三分之一屏幕，即使用户已有账号、只想授权也一样。左下方“最近授权任务”是大卡片，却经常只有零到一条记录。手机端新增表单被排到列表和历史之后，本次 390×844 下其顶部约在页面纵向 967px，首屏看不到。

建议：账号列表成为主区域；列表标题旁放明显的“添加账号”按钮，点击后打开抽屉或对话框。空状态直接提供该按钮。任务状态就近显示在对应账号下；全局历史保留为紧凑列表。手机使用页面自然滚动，避免账号列表内部再滚一层。

### 4. 字号偏小，颜色偏淡

实际输入框文字为 12.5～13.5px，表单标签 11.5px；浅色主题的辅助文字、边框和标签尤其淡。当前主按钮是白字配亮蓝青渐变，按声明的 OKLCH 色值计算，三个色点约为 4.20:1、3.02:1、2.34:1；这是色值估算，不是整张截图逐像素认证。14px 的按钮字不属于大字，应该按普通文字对比要求设计。

建议：正文 15px、辅助文字 12～13px、桌面输入框 14～15px，手机输入框至少按 16px 设计。为浅色主题单独设置较深的状态文字与辅助文字。普通文字与背景以至少 4.5:1 为目标，主按钮尤其要检查所有渐变位置。最省事的处理是换成较深的纯色按钮。

### 5. 有真实排版缺陷

本次 1280×720 中，国家输入框右边界为 1020.61px，语言输入框左边界为 1012.61px，**实际重叠 8px**。Grid 声明虽然有间距，但内部控件溢出了列宽。保存按钮下方说明直接把文字和多个 `<code>` 作为 flex 子项，句子被拆成几块，导致别扭的换行。已有两个账号时，“添加账号”角标初次仍显示 `ACCOUNT_1`，与实际新增槽位不一致。

优先修补示意：

```css
.field__control {
    width: 100%;
    min-width: 0;
}
.field-row {
    grid-template-columns: repeat(2, minmax(0, 1fr));
}
.form-note {
    align-items: flex-start;
}
.form-note > span {
    min-width: 0;
}
```

同时把提示句完整包进一个 `<span>`，使其中的 `<code>` 继续按普通行内文字排版。首次应用账号数据后同步更新表单槽位，或从默认界面中移除这个内部编号。

### 6. 手机端更像压缩后的桌面页

本次无横向溢出，这一点合格。但顶部工具区占约 177px；账号操作按钮仍为 30px 高，列表内有独立滚动，新增表单靠后，视觉密度与操作负担都偏高。

建议：移动端顶部只保留品牌、更多菜单与必要状态；完整实例路径移到设置。按钮触控高度建议 44px，常用动作保留一个，其他进入菜单。这里的 44px 是舒适性建议：不能把现有 30px 按钮直接说成不满足 WCAG 2.2 AA 的 24px 最小目标要求。窄屏下新增账号入口应在首屏可见。

## 建议采用的统一设计规格

| 项目 | 建议 |
| --- | --- |
| 风格 | 中性色、克制、清晰的本地工具，参考 CDK 的留白和层级 |
| 背景 | 深浅主题各一个稳定的中性色；工作台无持续背景动效 |
| 强调色 | 一个主要色；成功、待处理、失败另用语义色 |
| 圆角 | 输入框与按钮 8～10px，容器 12～16px |
| 文字 | 页面标题 22～24px，分区标题 16～18px，正文 15px，辅助 12～13px |
| 间距 | 使用 8、12、16、24、32px 为主的统一尺度 |
| 主要操作 | 添加账号、连接/重新授权；签到作为独立且明确的动作 |
| 输入项 | 默认只暴露当前流程必需信息，代理/TOTP/指纹归入高级设置 |
| 状态 | 每账号一行状态摘要；错误旁边给恢复动作 |
| 技术细节 | 路径、Cookie 数、`.env`、权限及内部编号放在详情与设置 |

建议文案替换：

- “先连接上游脚本” → “连接本机服务”。
- “脚本仓库根目录” → “安装目录”。
- “成功以会话文件实际写入为准” → 删除常驻说明，任务成功后显示“登录状态已保存”。
- “移动端 · 21 cookies · 刚刚” → “手机会话已保存 · 刚刚”；Cookie 数放进详情。
- “写入实例目录的 .env，供上游脚本授权时使用” → 改为说明实际登录方式和下一步，内部文件路径放进帮助。

## 合格前的修改顺序

1. 修复密码重启失效与退出凭证复活，补相应独立回归。
2. 修复自检误报、目标路径选择和空/损坏会话成功判定。
3. 实际部署并接通上游，验证真实账号与会话复用。
4. 修复输入框重叠、提示句碎裂、槽位显示和按钮对比度。
5. 精简账号标签、常驻表单和技术文案，重新安排手机首屏。
6. 最后统一颜色、字号、圆角和动效。此时再谈“精致”，收益更大。

完成前 4 项，才适合再次申请功能验收；再完成 5、6 项，才接近我认为 8 分以上的视觉完成度。这个审美目标是主观标准，不是保证分数的机械清单。
