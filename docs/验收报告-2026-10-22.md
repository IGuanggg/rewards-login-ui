# Rewards 登录面板验收报告

验收日期：2026-10-22。检查对象：当前目录的 `rewards-login-ui`。

## 结论

**未达到可直接交付使用的标准。** 已完成本地面板、账号表单、手动登录子进程调用和日志展示的基本实现；当前目录中的完整部署、减少重复输入、可靠状态反馈和访问保护尚未达标。

这版的入口填写的是脚本目录和 Control API 令牌，并非微软账号登录页。保存账号后，“登录”按钮启动上游 `manualLogin.js`；上游明确要求用户在弹出的浏览器中完成微软登录，面板没有接入自动填写邮箱、密码的流程。因此，它减少了编辑 `.env` 和输入命令的操作，但如果需求是“填一次账号，以后尽量不用重复输入”，目前仍未满足。首次授权、验证码及二次验证需要用户参与，不能以彻底免验证作为验收条件。

## 必须修复的问题

### 1. P1：所谓“管理员令牌”不保护面板接口

位置：`server.js:757`、`server.js:789`；前端请求函数 `public/js/app.js:53`。

服务没有在账号、配置、登录和运行接口前校验访问身份。设置令牌后，不携带令牌的 `GET /api/accounts` 仍返回 200；不携带令牌的 `PUT /api/config` 也能返回 200 并替换已有令牌。当前令牌只在 `proxyControl` 中用于请求上游 Control API。

影响：页面的“登录”不能限制面板访问。若保留管理员登录的产品含义，需要独立的面板认证，并保护全部敏感接口和 SSE；Control API 令牌应与面板访问凭据区分。如果只做免认证的本机工具，则必须明确说明，不能显示“已启用访问令牌”“需要令牌”等与实际不符的提示。

### 2. P1：没有保存会话也能显示登录成功

位置：`server.js:606`，尤其 `server.js:611`。

当前逻辑允许“子进程退出码为 0，且日志中没有 error”直接成为 `done`。测试脚本只输出一行普通日志、没有写入任何会话，最终任务状态仍为 `done`。

修复要求：必须核实所选账号和平台的会话已保存或刷新；两端登录应分别核实移动端、桌面端。正常退出、用户取消、失败和会话保存成功需要有明确的区别。

### 3. P1：凭据可以注入额外的环境变量

位置：`server.js:205`、`server.js:267`、`server.js:271`。

账号密码未经换行检查即拼接到 `.env`。测试密码 `dummy\nREVIEW_INJECTED=1` 被接受，返回 201，并在文件中生成独立的 `REVIEW_INJECTED=1` 配置行。

修复要求：拒绝字段中的非法换行，使用与上游读取方式兼容的环境变量序列化；密码和代理凭据等自由输入字段均需覆盖。使用包含空格、引号、等号和其他特殊字符的测试值验证保存与读取一致。

### 4. P2：普通文件夹会被当成有效实例，并被写入 `.env`

位置：`server.js:746`、`server.js:789`。

探测函数虽然会检查仓库结构，但保存配置和后续写入仅检查目录存在。测试中，不含上游 `package.json` 和 `manualLogin.js` 的普通文件夹被接受，随后新增账号成功并在该目录创建 `.env`。

修复要求：连接和每个写入入口统一验证仓库结构。路径错误时就地提示，不应先显示“已连接”，到启动登录时才报缺脚本。

### 5. P2：自定义会话目录被忽略

位置：`server.js:397`。

面板将会话路径固定为 `sessions/sessions.db` 及其 `dist`、`src` 变体。上游允许在 `config.json` 中配置 `sessionPath`。测试将已有会话放入 `custom_sessions/sessions.db`，面板返回 `exists: false`、`count: 0`。

修复要求：与上游会话路径解析保持一致，同时将数据库读取异常反馈给界面。数据库里有 Cookie 只能表述为“已保存会话”，不能据此保证会话仍然有效。

### 6. P2：Control API 拒绝访问，界面仍会显示“接口在线”

位置：`public/js/app.js:236`。

后端遇到 HTTP 401 仍返回 `reachable: true`，表示网络可达。前端仅使用该布尔值判定可用，所以会把鉴权失败显示为“接口在线”。

修复要求：根据 HTTP 状态和健康响应区分可用、令牌错误、服务错误和网络不可达；未配置时应在运行按钮附近给出直接说明。

### 7. P2：编辑账号会擅自改变原有指纹设置

位置：`server.js:283`。

保存账号时总是写入 `SAVE_FINGERPRINT_MOBILE=true` 和 `SAVE_FINGERPRINT_DESKTOP=true`。测试仅修改账号地区，原有移动端 `false` 即被改成 `true`。

修复要求：保留未编辑的账号字段。新增账号可给出默认值；修改已有账号不应悄悄覆盖用户选择。

## UI 与参考项目的符合程度

参考 `linux-do/cdk` 的登录组件是居中的窄单列：小图标、欢迎标题、一个主要登录按钮，以及条款与隐私弹窗；主题以黑白和中性色为主。

当前已有截图与 CSS 则采用紫青渐变、极光背景、较大的卡片和双栏说明。它借鉴了液态按钮、圆角、细边框、主题切换及弹窗，但没有延续参考项目的主要布局和克制程度。**可以算部分参考，不能算高度贴近。** 用户要求的是“参考”，并不意味着必须像素级复制；若希望一眼像该项目，建议收敛为居中单列和中性色，把实例路径等配置放入首次设置或高级设置中。

界面信息也应调整：

- 将“本地实例连接”“微软账号授权”“签到运行”分别写清楚，避免用户将路径配置页误认为微软登录页。
- 主流程建议为：首次检查环境 → 添加账号 → 发起授权 → 显示会话保存结果 → 后续复用。已经提供的信息应尽量复用。
- 当前“退出”仅切换视图，未清除自动进入面板的本地记录；刷新后的行为需要与按钮文案一致。
- 窄屏 CSS 中有一处 `max-width 100%;` 缺少冒号，需要修正并实际复测布局。
